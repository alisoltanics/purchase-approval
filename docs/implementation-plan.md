## 3. Data model

All primary keys are UUID v4 except where stated. All timestamps are `timestamptz`, stored and served as UTC.

### 3.1 Tables

**company**: `id`, `name` (unique, not null).

**user** (`accounts.User`): `id`, `email` (unique on `lower(email)`), `password` (Django hash), `display_name` (1–120), `company_id` → company (not null), `role` (`employee`|`manager`, CHECK), `is_active`. Unique `(company_id, id)` (needed for composite foreign keys below).

**purchase_request**: 
* `id` (the public reference, D-03), `company_id`, `requester_id`, `title`, `vendor`, `description`, `amount` `NUMERIC(8,2)`, `currency` `CHAR(3)` default `'USD'`, `status` (`pending`|`approved`|`rejected`), `submitted_at`, `decided_by_id` null, `decided_at` null, `rejection_reason` null, `idempotency_key` UUID not null.

There is no separate event table (D-55). The activity history is derived from the `purchase_request` row.

### 3.2 Constraints the database enforces

| Rule | Constraint |
|---|---|
| Amount range and precision | `NUMERIC(8,2)` plus `CHECK (amount >= 0.01 AND amount <= 999999.99)` |
| Currency is USD | `CHECK (currency = 'USD')` |
| Status values | `CHECK (status IN (...))` |
| Text lengths after trimming | `CHECK (char_length(title) BETWEEN 1 AND 120)`, same for vendor; description 1–2000; reason 1–1000 when present |
| Decision fields consistent with status | `CHECK`: pending ⇒ `decided_by`, `decided_at`, `rejection_reason` all NULL; approved ⇒ `decided_by`, `decided_at` NOT NULL and reason NULL; rejected ⇒ all three NOT NULL |
| Requester cannot decide own request | `CHECK (decided_by_id IS NULL OR decided_by_id <> requester_id)` |
| Requester belongs to the request's company | composite FK `(company_id, requester_id)` → `user(company_id, id)` |
| Decider belongs to the request's company | composite FK `(company_id, decided_by_id)` → `user(company_id, id)` |
| Duplicate submission | `UNIQUE (requester_id, idempotency_key)` |
| Edits/deletes of submitted data | Not a DB rule. Enforced by having no update/delete endpoint, and no code path that changes input fields |

### 3.3 What the database cannot enforce (server code must)

* Trimming and the single-line / control-character rules (D-26, D-27); the checks above only bound length.
* That the decider's role is Manager (needs a trigger; not used). Enforced in the service layer and covered by tests.
* Visibility (company and employee-own filtering). Enforced in one queryset function used by every read and write.

### 3.4 Indexes

`purchase_request (company_id, status, submitted_at DESC, id DESC)` and `(requester_id, submitted_at DESC, id DESC)` for the two list shapes.

## 4. Server-side rules

### 4.1 Authorization and company isolation

* A single function `visible_requests(user)` returns the base queryset: employee → `company = user.company AND requester = user`; manager → `company = user.company`. Every read (list, detail) and every decision starts from it. No view reads `PurchaseRequest.objects` directly.
* Detail, approve, reject look up the id inside `visible_requests(user)`. A miss (nonexistent, malformed UUID, other company, colleague's) yields the same 404 (D-10). The id parsing happens inside the lookup so a malformed id and a missing id are indistinguishable. Also an unknown `/api/…` path returns a JSON 404 in the standard error shape.
* Counts and `page_count` come from the same queryset, so they cannot include inaccessible rows (AC-22).
* The server derives company, requester, role and decision actor from `request.user` only (D-19, AC-24).
* `can_decide` is computed in the detail response by the same function that the decision endpoint uses, so UI and server cannot disagree.

### 4.2 Validation

* One module `common/validators.py` implements D-25..D-30. Serializers call it; they add no rules of their own.
* The frontend has `frontend/src/validation/` implementing the same rules. Both run the same `testdata/validation-cases.json` in their own test suite. A rule change requires a fixture change first.
* Pitfalls: JS `.length` counts UTF-16 units, so an emoji counts as 2; use code points. Do not use `str.strip()` or `trim()`: implement the explicit list from D-25 (they differ on U+001C–001F, U+0085 and U+FEFF; the fixture contains cases that fail a built-in implementation). A lone surrogate from JSON would crash the database insert, so it is rejected. Amount must be parsed as a string, never through `float` or `Number`.

### 4.3 Concurrency, duplicates, transactions

* **Submission** (one `transaction.atomic()`): look up existing by `(requester, idempotency_key)`; if found, compare normalized payload → return existing (200) or 409. Otherwise insert the request row. If the insert races and violates the unique constraint, catch `IntegrityError`, re-read, and apply the same compare. The submission "event" is the row itself, so a request cannot exist without it.
* **Decision** (one `transaction.atomic()`): fetch from `visible_requests` with `select_for_update()`, run checks in D-18 order, set status/decider/time/reason in one UPDATE, return. The second concurrent caller blocks on the row lock, then sees non-pending and gets 409 with current state. The CHECK constraint on decision fields is a second line of defense.
* `decided_at` uses one `now()` value taken once inside the transaction.
* `ATOMIC_REQUESTS` stays off; transactions are explicit in the service functions so response rendering never runs inside a lock.
* A failure while saving a decision leaves the request Pending with all decision fields empty (AC-29). A test forces this failure.

## 5. API design

Base path `/api/`. JSON only. All responses `Cache-Control: no-store`. CSRF is required on every unsafe method, including login.

### 5.1 Endpoints

| Method and path | Auth | Purpose | Success |
|---|---|---|---|
| `GET /api/health/` | none | liveness + DB check | 200 `{"status":"ok"}` |
| `GET /api/auth/csrf/` | none | sets `csrftoken` cookie | 204 |
| `POST /api/auth/login/` | none | `{email, password}` | 200 `{user}` |
| `POST /api/auth/logout/` | session | end session | 204 |
| `GET /api/auth/me/` | session | current user | 200 `{user}` |
| `GET /api/requests/?status=&page=` | session | list | 200 list envelope |
| `POST /api/requests/` | session | submit; header `Idempotency-Key` required | 201 created, 200 replay |
| `GET /api/requests/{id}/` | session | detail with activity | 200 |
| `POST /api/requests/{id}/approve/` | session | approve, empty body | 200 detail |
| `POST /api/requests/{id}/reject/` | session | `{reason}` | 200 detail |

No PUT/PATCH/DELETE route exists anywhere; other methods return 405 `method_not_allowed` (AC-27). A missing or non-UUID `Idempotency-Key` on submit gives 400 `validation_error` with field `idempotency_key`.

### 5.2 Shapes

```
user:     { id, email, display_name, role: "employee"|"manager", company: { id, name } }
list:     { count, page, page_size: 20, page_count, results: [ listItem ] }
listItem: { id, title, vendor, amount: "25.00", currency: "USD", status, submitted_at,
            requester: { id, display_name } }
detail:   listItem + { description, decided_by: {id, display_name}|null, decided_at|null,
            rejection_reason|null, can_decide: bool,
            events: [ { type, actor: {id, display_name}, created_at, reason|null } ] }   # derived, see below
```

`page_count` is at least 1 (an empty list is page 1 of 1). `can_decide` is true only for a manager, not the requester, on a pending request. The UI shows "Another manager must review your request." when `status = pending`, caller is a manager and `requester.id == me.id`.

### 5.3 Error format (frozen by T01)

```
{ "error": { "code": "<machine_code>", "message": "<safe human text>",
             "fields": { "<field>": [ { "code": "...", "message": "..." } ] },   # only for validation_error
             "request": <detail> } }                                              # only for already_decided
```

| HTTP | code | When |
|---|---|---|
| 400 | `validation_error` | field rules, malformed JSON, bad query parameters, missing idempotency key |
| 401 | `not_authenticated` | no or expired session |
| 401 | `invalid_credentials` | login failure; message `Email or password is incorrect.` |
| 403 | `csrf_failed` | CSRF check |
| 403 | `not_permitted` | employee attempts a decision on own request |
| 403 | `own_request` | manager attempts to decide own request |
| 404 | `request_unavailable` | message `Request unavailable. It may not exist or you may not have access.`; used for every inaccessible request id. Unknown `/api/` paths return 404 `not_found` instead |
| 405 | `method_not_allowed` | unsupported method |
| 409 | `already_decided` | message `This request has already been decided.`; includes `request` |
| 409 | `idempotency_conflict` | same key, different payload |
| 500 | `server_error` | generic message, no stack trace, no echo of input |

Login field errors for missing email/password use 400 `validation_error` with `fields`. Logging must never record request bodies or passwords (PRD S1): no body logging, and the exception handler logs only code, path and exception class.

### 5.4 Check order

* Reads: authenticated → visible (else 404).
* Submit: authenticated → CSRF → idempotency key present → field validation → create/replay.
* Decisions: D-18.
* Pitfalls: DRF session authentication returns 403 for anonymous requests by default; D-20 requires 401. CSRF cookie rotates at login, so the client must read the cookie freshly for each request. Django's default HTML error pages must be replaced by the JSON handler for everything under `/api/`.

## 6. Authentication and session handling

* Django session backend in PostgreSQL (`django.contrib.sessions`, DB sessions). Cookie `sessionid`: HttpOnly, SameSite=Lax, Secure from `COOKIE_SECURE`. `SESSION_COOKIE_AGE = SESSION_IDLE_SECONDS`, `SESSION_SAVE_EVERY_REQUEST = True` (sliding).
* Login: `GET /api/auth/csrf/`, then `POST /api/auth/login/`. Use `django.contrib.auth.authenticate` (hashes even for unknown emails) and `login()` (rotates session key, preventing fixation). Inactive users cannot log in.
* Logout: `POST` → `logout()` flushes the session row. Client clears the TanStack Query cache and navigates to `/login`.
* Refresh: the SPA calls `/api/auth/me/` on boot; 200 restores the session, 401 goes to sign-in.
* Expiry: the next API call returns 401 `not_authenticated`; the client follows D-34. A write that arrives after expiry is rejected before any state change (authentication runs first).
* Back navigation: D-35. The SPA never persists API data to local storage or session storage.

## 7. Frontend design

### 7.1 Routes

| Route | Screen | Notes |
|---|---|---|
| `/login` | S1 | reads `next` (D-33); signed-in users are redirected to `/requests` |
| `/requests` | S2 | `?status=&page=` |
| `/requests/new` | S3 | |
| `/requests/:id` | S4 | |
| `/` and unknown | redirect to `/requests` | unknown API ids render the neutral state, not a 404 page |

All routes except `/login` sit inside a guard that requires a session and renders the shell (product name, company, display name, role, Sign out, link to Requests).

### 7.2 State

TanStack Query holds server state with `retry: false` for mutations; list queries keyed by `(status, page)`. URL holds list state. A single `ApiClient` adds the CSRF header, parses the error format, and on 401 triggers D-34. No data is cached in browser storage.

### 7.3 Per-screen states (all from the PRD)

* **S1** idle / field errors (inline, per field, email kept) / submitting (button disabled, status announced) / invalid credentials (generic message) / service failure (retryable, distinct text).
* **S2** loading (never flash empty) / empty with New request / filtered empty with Clear filter / error with Retry / data. Managers see requester column; employees do not. Previous/Next disabled at ends; "Page X of Y" indicator.
* **S3** fields with visible labels; amount hint (`Use a period, up to two decimals, e.g. 25.50`) and fixed `USD` label; submit disables during request; on first invalid field after attempt focus moves there; success navigates to details with "Request submitted."; failure keeps values with retry; Cancel / in-app navigation prompts discard when dirty (D-38).
* **S4** loading / error with Retry / neutral unavailable with Back to Requests / Pending, Approved, Rejected displays; decision controls per `can_decide`; own-request info text; Approve confirmation (title and amount shown); Reject dialog (empty on every open, reason retained after network failure only); on 409 the dialog closes, "This request has already been decided." is shown and the detail is replaced by the `request` in the error.
* Activity list (derived from the request row): oldest first, event, actor, UTC timestamp, reason on rejection.

### 7.4 Error handling

Definite API errors map to inline field errors or banners from `copy.ts`. Network failures and 5xx show a retryable message and never claim success. After a decision mutation with an uncertain outcome, the retry button re-fetches the detail first and only offers the action again if the request is still pending (reconciliation, PRD §9).

### 7.5 Accessibility and narrow width

* Every input has a visible `<label>`; errors use `aria-describedby` and `aria-invalid`.
* Status badges contain text. Success/error banners use `role="status"` / `role="alert"` in persistent live regions. Loading uses `aria-busy` plus text.
* Dialogs use Radix Dialog: focus enters, trapped, returns to the trigger on close.
* All controls are native buttons/links/inputs, so keyboard operation and focus ring work; the focus style is explicit in CSS.
* At width 390 px the list switches to stacked cards, the UUID wraps (`overflow-wrap: anywhere`), and no element may make `document.documentElement.scrollWidth > innerWidth`. A Playwright check asserts this on each screen.
* User text is rendered only through React text nodes; line breaks are preserved with `white-space: pre-wrap`. `dangerouslySetInnerHTML` is forbidden (ESLint rule).
* Timestamps formatted by a single helper to `10 Oct 2026, 14:30 UTC` (UTC fields, English month abbreviations hard-coded, not locale-dependent). Amounts displayed as `USD 25.00`, built from the API string without numeric conversion.

## 10. Containerization and deployment

### 10.1 Images

`Dockerfile` stages:
1. `frontend-build` (`node:22-alpine`, pinned digest/tag): `npm ci`, `npm run build`.
2. `runtime` (`python:3.12-slim`, pinned): create non-root user `app` (fixed UID 10001), install `requirements.txt` (no dev deps), copy `backend/`, copy `frontend/dist` to `backend/static_spa/`, run `collectstatic` at build, `USER app`, `EXPOSE 8000`, `CMD gunicorn config.wsgi --bind 0.0.0.0:8000 --workers 2`.
* No secrets, `.env` files or demo passwords in any layer. `.dockerignore` excludes `.env*`, `node_modules`, `.git`, tests data not needed at runtime.
* Tags per D-52. A dev/test target (`--target test`) adds dev requirements and Playwright is run from a separate `e2e` service image based on the official Playwright image.

### 10.2 Compose (D-48)

| File | Services and settings |
|---|---|
| `compose.yaml` | `db`: `postgres:16`, volume `pgdata:/var/lib/postgresql/data`, healthcheck `pg_isready`, no published port. `app`: built from Dockerfile, `depends_on: db: condition: service_healthy`, healthcheck calling `/api/health/`, env from variables below, one internal network `internal` |
| `compose.dev.yaml` | publishes db on `127.0.0.1:5432`, bind-mounts `backend/`, `runserver` instead of Gunicorn; frontend run with `npm run dev` on the host (proxying `/api`) |
| `compose.test.yaml` | db on `tmpfs`, `app` as in base with `DJANGO_ENV=test`, extra `e2e` one-off service on the same network |
| `compose.staging.yaml` | `app.image: ${IMAGE_REPO}:${IMAGE_TAG}` (no build), `env_file: .env.staging` (ignored by git), `restart: unless-stopped`, published `${APP_PORT}:8000`, db port unpublished, `pgdata` external-style named volume that releases never remove |

Startup ordering: `db` healthy → one-off `migrate` → `app` up. The app itself does not migrate.

### 10.3 Persistence

Database data is on named volume `pgdata`. Release scripts use `docker compose up -d` and never `down -v` or `volume rm`. `deploy/backup.sh` runs `pg_dump` before each release. Redeploy of a new image with the same volume keeps data (PRD §14).

### 10.4 Configuration (names only)

`DJANGO_ENV` (dev|test|staging), `DJANGO_SECRET_KEY`, `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, `COOKIE_SECURE`, `SESSION_IDLE_SECONDS`, `DATABASE_URL` (or `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`), `APP_PORT`, `IMAGE_REPO`, `IMAGE_TAG`, `SEED_DEMO_PASSWORD`, `ALLOW_SEED_RESET`, plus smoke-test variables `SMOKE_BASE_URL`, `SMOKE_EMPLOYEE_EMAIL`, `SMOKE_MANAGER_EMAIL`, `SMOKE_PASSWORD`.
* `.env.example` lists names with empty values and is committed. Real files `.env`, `.env.staging` are git-ignored, mode 600 on the host.
* Staging secrets and demo password are created on the host by the operator and passed to the team lead through the agreed channel (D-46). The Django secret key and database password are generated randomly per environment.
* `DEBUG` is always false outside `dev`.

### 10.5 Release procedure (documented in `deploy/README.md`, scripted where simple)

1. CI/dev machine: run lint, type checks, unit and API tests, E2E on the test stack.
2. Build the image, tag with git short SHA, push to `IMAGE_REPO`.
3. On staging host: record current tag in `deploy/.previous-tag`; run `deploy/backup.sh`.
4. `docker compose -f compose.yaml -f compose.staging.yaml pull`.
5. `docker compose … run --rm app python manage.py migrate`.
6. First release only, or after an agreed reset: `docker compose … run --rm app python manage.py seed_demo` (idempotent). `--reset` only after the team has agreed (D-45).
7. `docker compose … up -d`; wait for the `app` health status healthy.
8. `deploy/smoke.sh` (health check, then Playwright smoke journey, AC-32).
9. **Rollback:** set `IMAGE_TAG` to `.previous-tag`, `up -d`. If the release applied a schema migration, restore the pre-release dump first (migrations are forward-only, D-51). Re-run smoke.

### 10.6 One setup for dev, tests and CI

* Dev: `docker compose -f compose.yaml -f compose.dev.yaml up db` plus local `runserver` / Vite, or the full stack.
* Backend tests: `docker compose -f compose.yaml -f compose.test.yaml run --rm app pytest`.
* E2E: `docker compose -f compose.yaml -f compose.test.yaml up -d --wait`, run `migrate`, seeds, then `run --rm e2e`.
* CI runs exactly these commands. A `Makefile` in the repo root wraps them (`make test`, `make e2e`, `make lint`), owned by T00.

| Risk | Mitigation |
|---|---|
